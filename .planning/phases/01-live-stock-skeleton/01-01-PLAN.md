## Phase Goal

**As a** shopper, **I want to** see the shop's current in-stock pieces on the live site, refreshed within seconds of any stock change, **so that** I never chase a piece that has already sold.

<objective>
Build the walking skeleton: an empty repo becomes a Next 16 app whose home page lists live How many stock through one tagged, cached fetch, and a signed `store.updated` webhook refreshes it within seconds. Everything is proven end to end on `next start` against a mock API (OpenNext cannot build on Windows; Plan 03 proves the same script on workerd in CI, Plan 04 on the deployed Worker).

Purpose: prove the riskiest architecture (tag cache + webhook revalidation + zero build-time calls) before anything else is built on it.
Output: scaffold, data seam, request-time page, webhook route, mock API and the `prove-freshness` script every later plan reuses.

Why the tracer touches many files: the repo has no `src/` and no `package.json`, so the first slice creates the project. Three of its files are copies (tsconfig, .gitignore additions, lockfile generated by npm). Each authored file is under about 80 lines.
</objective>
