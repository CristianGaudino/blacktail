## Phase Goal

**As a** shopper, **I want to** browse, filter, search, sort and page through the shop's in-stock pieces in the Blacktail Archive look on desktop and phone, **so that** I can quickly find pieces in my size, brand and budget.

<objective>
Turn the plain list into the mockup's card grid and add numbered pages. After this plan a shopper sees branded cards (photo, brand, title, colour and size, price in the shop's currency, a NEW badge on fresh pieces) that never shift while photos load, and can step through pages of 24.

Purpose: CAT-01, CAT-07, CAT-10 and SHELL-05 on screen. The pure rules (formatMoney, isNew, pageCountOf, resolvePage, pageLinks) are already written and unit-tested by Plan 04; this plan wires them into /shop. The loading skeleton changes how errors stream, so the Phase 1 outage proof is adjusted in the same plan.
Output: ItemCard, ItemGrid, Pager, /shop/loading.tsx, an outage proof that understands streaming.

Runs in wave 4 beside Plan 06 (header and phone menu). The two share no file. Do not edit src/lib/copy.ts, src/lib/money.ts, src/lib/dates.ts, src/lib/paging.ts, src/app/layout.tsx or src/styles/globals.css here; read COPY.catalogue, COPY.pager and COPY.stock as written by Plan 03.
</objective>

## Accepted deviation from the UI-SPEC: the past-the-last-page redirect (owner-visible)

- UI-SPEC State Coverage row "error, list-collection (page past the last page)": "A 307 redirect to the last page".
- What ships: the page calls `redirect(pageHref(query, last))`. Task 2 proves this is a real HTTP 307 to `/shop?page=<last>` while no loading.tsx exists. Task 3 then adds the loading.tsx the same UI-SPEC requires (Loading row); from that point the shell streams with HTTP 200 before the page knows the total, and Next emits the redirect as a meta refresh inside the stream (RESEARCH Pitfall 5, citing Next's redirect docs). The shopper lands on the last page either way; only the status code differs.
- Why the 307 cannot also hold after Task 3: the decision needs the API total before the first byte, so it would need either no loading.tsx (contradicts the UI-SPEC Loading row) or a `proxy.ts` that reads the API before render (ruled out by CLAUDE.md "What NOT to Use": no middleware or proxy in v1; it would also add an API read in front of every /shop request).
- Status: accepted by the planner on the research recommendation, and flagged for the owner: the phase PR body lists it (Plan 10) and this plan's SUMMARY repeats it. If the owner prefers the 307, the change is local: delete src/app/shop/loading.tsx.
- Checks: Task 2's automated command requires exactly `307 http://127.0.0.1:3000/shop?page=2`; Task 3's accepts that 307 or a refresh meta tag pointing at page=2, and nothing else.
